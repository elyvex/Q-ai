<objective>
Add the tool-authoring lifecycle: a durable, ordered describe → review → generate → test → security-review → approve → publish → revoke flow whose published result is immediately callable and immediately revocable over HTTP.

Purpose: R3 has no backend at all — `tool-registry` only exposes a fixed compiled table of 22 tools, and `tool-sdk`/`tool-sandbox`/`approvals`/`policy` are four-line placeholders. The only honest lifecycle this repository can ship is a **declarative composed tool**: the "generate" step produces a validated JSON step list over already-registered read-only tools (no codegen, no execution engine, no new dependency), "test" runs that list once through the real dispatcher and records the checksum, "security-review" applies a deny-list derived from the very predicates the HTTP tool route already uses, and "publish" makes the stored spec resolvable by a run route while "revoke" removes it from the callable set on the next request.
Output: a forward-only migration, `application::tool_lifecycle`, and the `/api/v1/tools/*` surface.

**Route shape (locked by 14-CONTEXT.md):** `/api/v1/tools/*`, durable writes deny-by-default with audit.
</objective>

    `pub trait ToolLifecycleApi: Send + Sync` with `create`, `list`, `get`, `review`, `generate`, `test`, `security_review`, `approve`, `publish`, `revoke`, `run`. `pub struct SqliteToolLifecycleService { db_path: String, tools: Arc<ToolRegistry>, graph: Arc<ToolRegistry> }` with `new(db_path, tools, graph)`.

    State machine (`advance`): allowed edges are `(none → drafted)`, `(drafted → reviewed)`, `(reviewed → generated)`, `(generated → tested)`, `(tested → security_reviewed)`, `(security_reviewed → approved)`, `(approved → published)`, and `(published → revoked)`; every other transition is `OutOfOrder { expected, actual }`. `revoke` is also allowed from `approved` so a never-published draft can be withdrawn. Implement it as one `const EDGES: [(&str, &str); 8]` table plus a lookup — no nested `match` duplication.

    Each mutation runs in one `SqliteDatabase::write()` UnitOfWork that (a) writes the state/spec change, (b) inserts the `tool_lifecycle_steps` row, (c) stages one `AuditedMutation` (subject `SubjectRef` for urn `tool:{name}`, actor `Actor::System { name: "qai-serve" }` unless an approver is supplied), then commits. `approve` additionally calls `uow.sources().insert_approval(ApprovalRow { subject_urn: "tool:{name}", kind: "tool.publish", decision: Some("approved"), request_payload: canonical spec JSON, decision_note, decided_by: ensure_principal(approver), .. })` in the same UnitOfWork.

    Security-review rules (pure `fn review_spec(&ToolSpec, &ToolRegistry) -> Result<(), ToolLifecycleError>` in this module so it is unit-testable without a DB): name matches `^[a-z][a-z0-9_.-]{2,64}$` and is not in `TOOL_NAMES`/`ISNAD_TOOL_NAMES`/`RAG_TOOL_NAMES`; description non-empty and ≤ 500 chars; `steps` non-empty and ≤ 8; every `step.tool` is in `TOOL_NAMES` or the read-only isnad subset and is rejected when `is_mutating_rag_tool`/`is_mutating_isnad_tool` is true; every string value in `step.params` equal to `"$query"` is the only permitted placeholder and any other `$`-prefixed string is refused with the offending key named.

    `run(name, query)`: read the row, refuse unless `state == "published"` (`Denied` → `QAI-TOOL-0309`), substitute `"$query"` occurrences with the caller's query, then for each step call `dispatch_registered_tool(&self.tools, &self.graph, &step.tool, params)` and collect `{tool, result, research_checksum}`; return `{name, steps: [...]}`. Any step failure aborts with `RunFailed { code, detail }` carrying the original `QAI-*` code.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → /api/v1/tools | author-supplied name, description, step list, query |
| published spec → dispatcher | a stored spec becomes live tool execution |
| lifecycle → audit/approvals | durable writes must be attributable |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-14-11 | Elevation of privilege | published spec | critical | mitigate | Steps may only name read-only registered tools; mutating names are refused by the same `is_mutating_*` predicates the tool route uses; unknown and shadowing names refused; no codegen and no sandbox |
| T-14-12 | Tampering | lifecycle order | high | mitigate | Single `EDGES` table; every gate re-reads state from the DB row inside the write UnitOfWork; a stale client cannot force an out-of-order step |
| T-14-13 | Spoofing | approval | high | mitigate | `approve` requires a non-empty approver, seeds the principal via `ensure_principal`, and writes the `approvals` row in the same UnitOfWork — no approval without an identity |
| T-14-14 | Repudiation | lifecycle mutations | high | mitigate | One chained audit event per persisted mutation, staged before commit; test asserts count equals mutation count |
| T-14-15 | Denial of service | `/tools/{name}/run` | medium | mitigate | Step list capped at 8, params capped by the existing 1 MiB request-body layer, execution bounded by the 30 s request timeout |
| T-14-16 | Information disclosure | spec echo | low | mitigate | Spec is author-supplied and returned verbatim; no other tenant data is reachable through the routes |
| T-14-SC | Tampering | schema change | high | mitigate | One forward-only migration, append-only (`migrate-check`), no external dependency added |
</threat_model>
