<objective>
Build the three operating surfaces the phase promises — Tool Studio, Source Catalog, Operations (with the RAG project manager) — as real working interfaces over the chunk-1 routes, each showing inputs, outputs, gate verdicts and audit state, and each refusing to look successful when the server denies.

Purpose: R3, R4, R5 and R15 have HTTP backends as of 14-03/04/05/06 but no UI. The design rule that shapes all three views is the repo's: durable writes are deny-by-default and audited, so the UI's job is to show exactly what the server decided — state, verdict, code, audit sequence — and never to paint an optimistic success. One shared pattern covers all of it: a mutation returns the row (or a typed error), the view repaints from the response, and a 403 renders as a refusal row naming the CLI verb rather than a disabled button with no explanation.
Output: four typed client modules, three views, three routes registered in all four places, and the four retargeted reachability rows.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → /api/v1/{tools,catalog,ops,rag} | operator-typed names, steps, reasons, approvers, paths and confirmations cross here |
| server responses → rendered state | lifecycle state, verdicts, audit sequences and job state become the UI's truth |
| browser → clipboard | CLI pointers leave the page as text |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-14-58 | Elevation of privilege | approve / activate / publish / repair | critical | mitigate | The UI only calls the routes; it adds no bypass, requires the confirmation modal naming the target, sends an explicit approver/`confirmed: true`, and renders a 403 as a refusal — the server's deny-by-default remains the only gate |
| T-14-59 | Tampering | optimistic state paint | high | mitigate | Every mutation repaints from the response body; a failed call leaves the previous row and shows the error, so a refused transition cannot look applied |
| T-14-60 | Repudiation | lifecycle transitions | high | mitigate | Where the response carries an audit sequence it is displayed; otherwise the view claims nothing. Operators can confirm the chain in the audit tab (`/ops/audit/verify`) |
| T-14-61 | Information disclosure | job detail / audit rows | medium | mitigate | Only the already-redacted `get_job` payload and audit fields are rendered; no raw checkpoint bodies or error stacks are printed beyond the documented keys |
| T-14-62 | Denial of service | list/table volume | medium | mitigate | Lists use the server's `limit` and print its truncation flag; no auto-refresh loops — refresh is an explicit control per tab |
| T-14-SC | Tampering | web dependencies | low | accept | No package added; build + `layer_separation` gate the change |
</threat_model>
