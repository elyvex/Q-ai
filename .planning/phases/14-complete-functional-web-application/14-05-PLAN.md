- `application::db::{list_jobs,get_job,list_audit_events}` open a read-only pool per call, redact payload/checkpoint/error columns, cap at 1000 rows and return `{items, truncated}`. `get_job` parses a worker cancellation disposition into a first-class `disposition` field.
- `request_job_cancel` accepts only `Queued/Leased/Running/Checkpointed/Interrupted`, stages `AuditAction::JobCancellationRequested`, and returns the still-running row — it never claims the worker stopped. `retry_job` accepts only `Failed/DeadLettered/Interrupted` and stages `JobRetried`.
- `application::audit_bridge::verify_persisted_audit(path)` returns `AuditVerificationReport { valid, checked_events, gaps, tampered_sequences }`.
- `run_quran_checks(&dyn storage::Database, deep)`, `run_index_checks(&SqliteDatabase, data_dir, deep)`, `run_quran_graph_checks(&SqliteDatabase, deep)` all return `Vec<QuranDoctorCheck { id, status, summary, remedy, next_command }>`; index checks need `application::quran_index::index_root_for_db(db_path)`.
- The three repairs take `(db_path, RepairInput|TombstoneGcInput|RebuildInput)` with `confirmed: bool` + `invoked_by: String`, return `RepairReport { operation, summary, …, audit_sequence, records }`, and already emit `AuditAction::DoctorRepairExecuted`.
- There is **no persisted doctor-run history table and no session store**. Do not invent one: report the run timestamp of the current response and derive "sessions" from live job leases; derive "last repairs" from `audit_events` where `action = 'doctor_repair_executed'`.
- `job_events` is written by nothing at HEAD; a job with no trace returns an empty list. Do not fabricate events.

    Implementation notes:
    - `jobs`/`job`/`cancel_job`/`retry_job` delegate to `crate::db::{list_jobs,get_job}` and `crate::job_queue::{request_job_cancel,retry_job}`, mapping `JobControlError::{NotFound,Ineligible}` to `0304`/`0305`. Do not re-implement job SQL.
    - `job_events` reads `SELECT sequence, level, stage, message, data_json, occurred_at FROM job_events WHERE job_id = ? AND sequence > ? ORDER BY sequence ASC LIMIT 1001` and redacts `data_json` through `domain::redaction::redact_json_value` after parsing.
    - `audit` reads `audit_events` with optional `subject_urn`/`action` equality filters and `sequence >= from_sequence`, ordered by sequence, limit 1001 → `{items, truncated}`; `audit_verify` delegates to `crate::audit_bridge::verify_persisted_audit(&self.db_path)`.

    - `sessions` groups `jobs` by non-null `lease_owner` with counts and min/max `lease_expires_at`.
    - `doctor` opens one read handle, runs `run_quran_checks(db, deep)`, `run_index_checks(db, &index_root_for_db(&self.db_path), deep)`, `run_quran_graph_checks(db, deep)`, tags each check with its family (`quran`/`index`/`graph`), and adds `last_repairs` from the five most recent `audit_events` with `action = 'doctor_repair_executed'` (sequence, occurred_at, subject).
    - `repair` refuses `confirmed: false` with `0300` ("pass confirmed: true …"), rejects an empty `invoked_by` (never invent a principal), and dispatches to the three existing repair functions, returning their `RepairReport`.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → /api/v1/ops | job ids, audit filters, repair actions |
| ops → audit/doctor | repair effects become durable, attributable state |
| ops read → redaction | job payloads may hold secrets |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-14-23 | Elevation of privilege | POST /ops/doctor/repair | critical | mitigate | Deny-by-default 403 unless the policy switch allows; `confirmed: true` required; operator principal required; the underlying repair functions already require both |
| T-14-24 | Information disclosure | job detail / events | high | mitigate | Reads go through `db::get_job` and `redact_json_value`; event `data_json` is parsed then redacted, so a secret sentinel in a payload cannot be returned |
| T-14-25 | Tampering | audit log | high | mitigate | Only reads are exposed; `audit/verify` recomputes the chain and reports gaps/tampered sequences rather than "fixing" anything |
| T-14-26 | Denial of service | doctor / audit listing | medium | mitigate | Doctor checks are the existing bounded implementations (deep is opt-in); listings cap at 1000 rows with a `truncated` flag |
| T-14-27 | Repudiation | job cancel/retry | medium | mitigate | Both delegate to functions that stage their own audit event in the same UnitOfWork |
| T-14-SC | Tampering | config/constant drift | low | mitigate | Router limits and the budget report share one set of `pub const`s; no dependency or schema change |
</threat_model>
