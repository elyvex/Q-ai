## Phase Boundary

Close the **engineering remainder that Phases 1, 2, and 3 left behind**, without
re-opening any closed phase and without inventing any owner decision.

This is an **evidence-driven brownfield gap-closure phase** in the exact posture
of Phase 4 (D-01): map every known-remaining item to current code plus a
repeatable check, preserve what already works, and create implementation work
only for genuinely missing behavior or weak evidence.

1. **Board/ledger drift.** The legacy boards under `docs/03-plan/phases/` were
   last reconciled 2026-09-24, *before* GSD plans 03-01…03-08 and 04-01…04-05

   `phase-04-quran-graph` still reads `0 / 30 ☑` after the phase completed. Two

2. **Genuinely unwritten Phase-2 engine work.** Ten `☐` rows and thirty-three `◐`
   rows on `phase-02-rag` are not all bookkeeping. Verified against the tree,
   the real engineering gaps are: the counting/discovery tool surface
   (`P2-T104`, `T101`, `T102`, `T109`), the nightly reconciliation job
   (`P2-T107`), the evaluation harness (`P2-T108`), the tool-contract
   conformance suite (`P2-T110`), the full soak (`P2-T111`), the documentation

**Non-negotiable boundary: this phase closes no owner decision.** `OD-01` …
`OD-14` all stay 🔴. Where a residual item is blocked on an owner input

<decisions>
## Implementation Decisions

### Scope, Posture & Finish Line

- **D-3.5-01:** Phase 3.5 is **evidence-driven brownfield gap closure**, same
  posture as Phase 4 D-01 and Phase 3 D-04. A residual item is in scope only if
  (a) named in a phase ledger, follow-up ledger, or verification report, and
  (b) still unimplemented when read against the live tree. An item already
  implemented is *reconciled*, not rewritten. — **Reversibility:** reversible —
  a planning-boundary choice.
- **D-3.5-02:** **The legacy boards are reconciled, not deleted.** They carry the
  detail GSD plans do not (per-task roles, estimates, deliverable IDs). The
  reconciliation is a truth-restoration pass: every row is re-read against the
  tree and flipped to ☑ / ◐ with evidence, or left open with a stated reason.
  After this phase no board row may contradict a committed SUMMARY. — **Reversibility:**
  costly — the boards are the historical record; rewriting history is not
  reversible even though a row flip is.
- **D-3.5-03:** **A single status system wins: `.planning/` is authoritative for
  phase state; `docs/03-plan/phases/*/tasks.md` is authoritative for task
  granularity.** `docs/06-progress/status.md`, `current-plan.md`, and
  `roadmap.md` become pointers, not parallel ledgers. Every future phase
  updates both in the same commit (this is already the Phase-0 ledger rule 4,
  extended). — **Reversibility:** costly — a split-brain status system is the
  single defect this phase exists to remove; reversing re-creates it.
- **D-3.5-04:** **Zero owner-decision closures.** Owner-gated residuals ship as
  *readiness* — the command that closes them, the evidence they will produce,
  and the row left 🔴. OD-01/02/03 (Phase 1 dataset + reviewer + reference
  corpus), OD-11/12 (morphology dataset + linguist), OD-04…OD-10, OD-13, OD-14
  are untouched. — **Reversibility:** costly — an invented approval is
  unrecallable and would launder a human gate into a machine pass.
- **D-3.5-05:** **Scope is capped at the ten named residual workstreams**
  (W1…W10 below). New work discovered during execution is recorded in a
  follow-up ledger, not silently absorbed. — **Reversibility:** reversible.

### Workstream Boundaries

- **D-3.5-06 (W4 counting/discovery):** The counting tail is **implemented to the
  same bar as the SC-aligned core** — typed errors, `CountingRules` on every
  numeric report, dataset attribution, CLI + HTTP parity, and never an empty
  report standing in for an unavailable capability. Ratifying the counting
  *rules* (ADR-0211) stays owner-gated; implementing the surface does not. —
  **Reversibility:** costly — these are published CLI/HTTP/tool surfaces.
- **D-3.5-07 (W6 evaluation harness):** The harness ships in the existing
  `crates/evaluation` placeholder rather than a new crate, with **metric
  definitions and a versioned dataset as committed fixtures** so a run is
  reproducible and a regression is diffable. It reports metrics; it does **not**
  enforce linguistic quality gates (that is the linguist's call, and
  ADR-0204/0211 are Draft). — **Reversibility:** reversible — additive crate
  content behind an existing manifest entry.
- **D-3.5-08 (W7 tool conformance):** The conformance suite runs over the
  **twelve registered `quran.*` tool names** actually present in
  `tool-registry`, not the legacy board's "22 Phase-2 tools". The board number
  is stale and is reconciled in W1; the suite tests what ships. — **Reversibility:**
  reversible — a test suite addition.
- **D-3.5-09 (W3 nightly reconcile):** The reconciliation job runs on the
  existing durable-job substrate (`jobs` crate, one UnitOfWork, checkpointed,
  audited) and is **read-only against canonical and derived data** — it reports
  drift, it never repairs. Repair stays an explicit confirmed command, matching
  the Phase 4 D-08 doctor/repair split. — **Reversibility:** costly — a new
  production job kind is operator-visible.
- **D-3.5-10 (W9 hardening):** `WR-*` items are fixed **only where the fix is
  a real precision or fail-closed bug**. Items that are genuine future
  capability (host liveness deadlines, in-memory queue fidelity) are recorded
  in the deferral ledger with a Phase 12 target rather than half-built. — **Reversibility:**
  reversible per item.
- **D-3.5-11 (W10 test gate):** The load-sensitive `lookup_performance_smoke`
  gate is made **robust, not relaxed** — median or p95 over warm repetitions
  with an isolated-run strict bound — so a busy machine stops producing false
  reds. No reader behavior is relaxed. — **Reversibility:** reversible.

### Agent's Discretion

- Fixture file layout and naming for the evaluation datasets, goldens, and
  conformance cases (follow the existing `fixtures/quran/**` convention).
- Exact CLI flag names and human-readable wording, following Phase 1 D-16.
- Whether the counting tail lands one tool per commit or per group.
- The order of independent test files within a workstream.

<constraints>
## Non-Negotiable Constraints

- **No fabricated scripture.** No golden row, fixture, or reference text is ever
  invented. Every Quranic string traces to a committed fixture or an
  owner-supplied import.
- **No invented owner approvals.** See D-3.5-04.
- **Canonical bytes are immutable.** No task may alter a canonical row, a frozen
  hash recipe (`qai-text-hash-v1`, `structure_hash`, `token_order_hash`), or an
  approval-gated write path.
- **No new dependencies without a legitimacy record.** Phase 3.5 is expected to
  add zero packages; if one becomes unavoidable it needs a `Cargo.lock` diff and
  a `deny.toml` pass recorded in the same commit.
- **Empty ≠ unavailable.** Any new surface fails closed with a typed error when
  its dataset is absent, never with an empty list or an empty 200.
- **Partial results are labeled.** Truncated output carries `truncated` plus a
  non-empty `incomplete_reason`; it is never rendered as absence.

</constraints>
