<objective>
Prove SC3/D-16 with a repeatable cross-surface golden gate: one shared fixture drives **every registered research tool — all 12 `ToolRegistry::TOOL_NAMES`** — through three distinct code paths — the shared service/registry call, the HTTP router, and the `qai` CLI binary — and asserts byte-identical normalized payloads and an identical `research_checksum` for each tool. The gate is a committed integration test so it is a repeatable check, not a one-time manual comparison.

Purpose: D-16 is the evidence mechanism for the phase's central success criterion ("identical results + research checksum"); "parity by construction" is only credible when it is proven against genuinely distinct paths for **every** tool, not a single representative one. All 12 tools reach the HTTP leg through one generic typed-tool route (`POST /api/v1/quran/tool/{name}`, plan 05-01 Task 2) so the HTTP leg carries the same canonical tool identity as the service and CLI legs.
Output: `crates/cli/tests/parity_cross_surface.rs` plus a CLI snapshot case, runnable via `cargo test -p cli --test parity_cross_surface`.

Tracer note: this plan expands from the contract proven in 05-01; it is not the phase tracer.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| process boundary (CLI) | The gate spawns an external binary; a stale/absent binary would silently pass or fail |
| cross-surface comparison | A format-skewed or tautological comparison would produce false parity |
| tool identity per surface | A differing tool identity (e.g. `quran.search_exact` vs `quran.search`) would make the comparison meaningless even when the bytes match |
