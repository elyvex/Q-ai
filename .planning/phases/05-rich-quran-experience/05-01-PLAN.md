<objective>
Complete the research result contract: add a required, payload-covering, domain-separated `research_checksum` to the shared `ToolResult` contract and ripple it through every registered tool, the HTTP `Meta`, the OpenAPI schema, and the CLI JSON output. Per D-14 the checksum covers inputs + tool identity + normalized parameters + result payload, reusing the frozen canonical-JSON + `sha256` recipe (ADR-0006) domain-separated per ADR-0108 style; per D-15 it is a required field on the shared contract.

Purpose: SC3 ("identical results + research checksum across UI, API, and CLI") is impossible while the existing `reproducibility.checksum` omits the result payload and normalized parameters (Pitfall 4). This plan closes that gap once, at the contract owner.
Output: `crates/tools` exposes `research_checksum`; all 12 registered tools populate it; `Meta`/OpenAPI and the CLI `quran tool` JSON path surface it.

Tracer: this phase leads with the thinnest end-to-end slice — `quran.get_ayah` carrying a real `research_checksum` from the service through the HTTP envelope, proven by a runnable check. Because `research_checksum` is a required (no-`Default`) field, Task 1 also migrates every remaining production `ToolResult` construction site in the same commit so the workspace compiles; Task 2 then completes the CLI leg (`quran tool … --json`) that the D-16 gate compares.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| service → HTTP envelope | Typed `ToolResult` is projected into the untyped `Meta.reproducibility`/`research_checksum`; a mismatch here is a silent reproducibility break |
| client → generic typed-tool route | An untrusted tool name + params body crosses here; resolving to a wrong tool (or decoding untrusted JSON) would break identity or crash the handler |
| CLI/consumer → stored checksum | A consumer recomputes and compares the checksum across surfaces; a nondeterministic serialization would forge or break reproducibility |
