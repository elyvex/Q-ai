<objective>
Close the two incomplete layers of D-13 and the uncovered activation/rollback branch of criterion 1. Today only three canonical tables carry triggers, and the `CanonicalWriter` + `ApprovalToken` gate is declared but has no implementor and a publicly constructible token — so the project's stated immutability invariant is dead code (Pitfall 1, QC-05, QC-06, QC-01).

Purpose: "Canonical tables reject all non-approved writes" must be true, not documented. The honest enforcement today is the trigger set plus the persisted-approval check inside `activate_edition`; this plan completes the trigger set, makes the token a real non-forgeable precondition of publication without rebuilding the frozen transaction, and proves the rejection branches for both activation and rollback.

Task ledger: `TASK-002-canonical-quran-core` (see `docs/04-tasks/`) — this plan is one implementation unit of that phase task.

Output: migration 0021, a completed type-level gate with a real implementor and caller, an importer code-path audit test, and rejection/invalidation coverage.
</objective>

<threat_model>
**Posture:** ASVS Level 1; any unmitigated `high`-severity threat blocks this plan — no auto-approval.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| any SQL client → canonical tables | Raw INSERT/UPDATE/DELETE can be issued outside the application; triggers are the last line of defence. |
| persisted approval row → canonical publication | Only a granted approval naming the exact edition URN may authorize a publication. |
| importer → staging | Untrusted manifest bytes reach staging only; the importer must never hold a publication capability. |
| operator → rollback | A rollback is a canonical pointer change and must be approval-gated exactly like activation. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
